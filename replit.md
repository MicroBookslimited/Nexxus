# NEXXUS POS

NEXXUS POS is a comprehensive Point of Sale (POS) system that unifies various business functionalities into a single application for small to medium-sized businesses.

## Run & Operate

*   **Install dependencies**: `pnpm install`
*   **Run development servers**: `pnpm dev` (starts both frontend and backend)
*   **Build all artifacts**: `pnpm build`
*   **Run typecheck**: `pnpm typecheck`
*   **Generate API client**: `pnpm -F api-server codegen`
*   **Push DB schema**: `pnpm --filter @workspace/db run push` (run from workspace root)

**Required Environment Variables**:
*   `DATABASE_URL`
*   `JWT_SECRET`
*   `PAYPAL_CLIENT_ID`
*   `PAYPAL_CLIENT_SECRET`
*   `POWERTRANZ_API_KEY`
*   `POWERTRANZ_MERCHANT_ID`
*   `QUICKBOOKS_CLIENT_ID`
*   `QUICKBOOKS_CLIENT_SECRET`

## Architecture decisions

*   **Unified Frontend**: A single React application (`artifacts/nexus-pos`) serves all user roles (POS, customer display, reseller portal, admin) via URL-based routing and lazy-loaded components, improving maintainability.
*   **Modular Backend API**: A RESTful Express API (`artifacts/api-server`) with distinct endpoints for various business domains ensures scalability and clear separation of concerns.
*   **Multi-Unit Sales**: Products can have multiple sale units. The POS captures quantity in base units, and the cart UI shows a badge with the selected unit. Different unit choices for the same product appear as separate cart lines.
*   **Variant Stock Tracking**: For single variant groups, stock is tracked per variant option. For two or more variant groups, stock is tracked at the combination level, with a dedicated `variant_combinations` table.
*   **Per-Product Tax Exemption**: Products can be marked `is_taxable`. Non-taxable products are excluded from the tax base. Discounts are proportionally applied to taxable and non-taxable buckets.
*   **Product Archive (Soft Delete) + Bulk Delete**: Products are never hard-deleted — deleting a product (single Trash2 button **or** the bulk "Delete selected" action) sets `productsTable.archivedAt` so all history (order_items, purchase_bill_items, accounting links) is preserved. Archived products are hidden from the catalog/POS (`GET /api/products` filters `archived_at IS NULL` unless `includeArchived=true`), the online menu (`public-menu.ts`), and the bulk price tool (`price-manager.ts` scope queries) — but reports intentionally do NOT filter (history must include archived items). Endpoints: `POST /api/products/bulk-archive` and `POST /api/products/bulk-restore` (both `{ ids: number[] }`, tenant-scoped, idempotent, audited). The products list (`pages/products.tsx`, list view) has per-row checkboxes + select-all, a selection action bar, and a "Show archived" toggle; archived rows show an "Archived" badge and a Restore button. **Gotcha**: the generated `includeArchived` query param uses `zod.coerce.boolean()`, which coerces ANY present value (incl. the string `"false"`) to `true` — the client must OMIT the param to get active-only, never send `false`.
*   **Purchase Bill Input Tax + Cost Prompt**: Each Purchase Bill carries a `defaultTaxRate` plus an optional per-line `taxRate` override; bills persist `subtotal`/`taxTotal`/`totalCost` and the line shows a Margin column (% and $). On confirm the server runs side effects in a single DB transaction (stock bump, stock movement, product cost update only when the new unit cost is *higher*, and a balanced journal entry: Dr Inventory `subtotal` + Dr Input Tax (`1250`) `taxTotal` = Cr AP `totalCost`). The server returns `costChanges` (one row per product, aggregated by `productId`) with a `suggestedPrice` that preserves the prior selling-price margin; the POS opens a dialog where the user can edit/skip individual price updates.
*   **Technician Role**: A restricted role for installers to set up customer POS systems, with impersonation capabilities and server-side route blocking for sales/financial operations.
*   **Supermarket Mode**: A global tenant setting (Settings → POS Security) that requires a manager/admin/supervisor PIN for cart-restricted actions (decrease qty, remove item, clear cart) when a cashier is logged in. Discount and price overrides are always gated by manager PIN. Managers/admins/supervisors bypass the gate.
*   **Price Manager**: Bulk price update tool at `/price-manager` (permission `pricing.manage`, also implicit for Owner/Admin). Supports three methods — percentage of current price, cost-based markup, and fixed amount — with optional rounding to nearest $5/$10/$50/$100/$1000. Scope is `all` / `category` / specific products. Workflow is preview → per-line override → apply; on apply the server enforces scope (rejects out-of-scope productIds), wraps product updates + an audit row in `price_change_logs` in a single transaction, and exposes a History tab. Server-side authz: every endpoint requires a `staffId` whose tenant matches the token and whose role grants `pricing.manage` (or is Owner/Admin); technician-impersonated tenant sessions are rejected.
*   **Time-Based Promotions**: Promotional prices on individual products that activate during a date/time window. Server-authoritative — `findActivePromoPrices()` in `routes/promotions.ts` is called from `orders.ts` BEFORE the volume-pricing tier lookup; when a promo is active the promo price replaces the regular price, `originalUnitPrice` is set to the regular price (so the receipt's "You Save" line auto-renders), volume tiers are bypassed, and any client-supplied per-line `itemDiscount` on a promo line is ignored ("replace and lock"). POS fetches `/api/promotions/active` (refetched every 60s) and merges promo prices into product cards (PROMO badge + crossed-out regular price). Managed at `/promotions` (permission `pricing.manage`). The receipt's tier-savings label was generalized from "(volume pricing)" to "You Save" so both promo and volume savings render under the same line.
*   **Batch / Lot / Expiry Tracking + FIFO/LIFO**: Opt-in per product via `productsTable.trackBatches`. The tenant-wide method is set in Settings → Inventory (`stock_method` setting, default `fifo`); per-product `stockMethodOverride` wins when set. Purchase-bill lines for batch-tracked products accept optional `batchNumber` + `expiryDate`; on confirm the server writes a row into `product_batches` (id, productId, batchNumber, expiryDate, quantityRemaining, receivedAt, sourceType=`purchase`, purchaseBillId). At checkout, `orders.ts` deducts `product.stockCount` as before (still authoritative for oversell guard) and then deducts the per-line quantity from `product_batches` ordered by `receivedAt` ASC (FIFO) or DESC (LIFO). If batches don't sum to `stock_count` (drift), a negative legacy batch is auto-created to reconcile. Toggling `trackBatches=true` on a product with existing stock auto-creates a single legacy batch for the current `stockCount` (PUT handler in `products.ts`). Expired batches do NOT block sales — they're tracked but not gated. GET `/api/product-batches?productId=&includeEmpty=` lists batches. Variant/composite products are out of MVP scope.
*   **Supplier Returns / Debit Notes**: Inverse of a purchase bill — used when goods are returned to the supplier. Two flavours: **bill-linked** (`purchase_bill_id` set, each line references a `purchase_bill_items.id`, qty capped at `originalQty - sum(prior confirmed returns)`, unit cost and tax rate copied server-side from the original line so the JE is a true mirror) and **standalone** (no bill, user enters product + qty + unitCost + taxRate freely). At confirm, side effects run in a single transaction: decrement `products.stockCount` (rejects oversell), for batch-tracked products decrement the user-chosen `product_batches` row (UI suggests FIFO = oldest non-empty batch), write a negative `stock_movements` row, and post a reversing JE — Dr AP (`2000`) `totalAmount` = Cr Inventory (`1200`) `subtotal` + Cr Input Tax (`1250`) `taxTotal`. Status flip is atomic (`UPDATE … WHERE status='draft'`). Drafts are deletable; confirmed returns are immutable for audit. Managed at `/supplier-returns` (permission `inventory.manage`); linked from the Purchase Bills section in `/products`. **Out of scope**: composite/variant products on returns, partial-batch splits, debit-note PDF, AP-credit balance integration (the JE reduces AP directly).
*   **Hardware Store POS Layout**: An alternative POS layout optimized for hardware/building-supply stores. Gated by a global tenant setting `hardware_ui_mode` (Settings → POS Interface). When ON, `/pos` renders `pages/pos-hardware.tsx` instead of `pages/pos.tsx`; when OFF, the standard layout is used. Both layouts share **all** cart/pricing/checkout/inventory logic — they reuse the same `useListProducts` / `useCreateOrder` / `useGetSettings` / `useGetCurrentCashSession` / `useListCustomers` / `useCreateCustomer` hooks, the same PIN-gate + open-shift guards, and the same `buildReceiptHtml` + `openReceiptWindow` + `receiptOrderFrom` receipt pipeline — only the visual layout differs. Hardware layout features: dark navy + teal/cyan gradient theme matching NEXXUS branding, prominent SKU/barcode search bar with scanner-friendly Enter-to-add, horizontal scrolling category cards with hardware icons (Wrench/Bolt/Lightbulb/Droplets/Hammer/PaintBucket/Trees/Boxes), a scannable product *list* (image + SKU + name + category + price + stock-badge + "+" button) instead of a card grid, a fixed 380px-wide right-side cart panel with inline qty controls and payment method toggle, and a bottom Quick Action bar (Quick Add / Recent / Discount / Price Check / Notes). Variant/modifier products fall through to a toast asking the user to use the standard POS — the hardware UI is for straightforward SKU items. The dispatcher lives in `App.tsx` as `<PosModeDispatcher />`, which simply reads `settings.hardware_ui_mode` and renders either `<POS />` or `<PosHardware />`.
*   **Variable-Length PIN + Magstripe Override Cards**: `PinPad` accepts 4–8 digit PINs (auto-submits only at max length; otherwise the Enter button submits once `minPinLength` is met) and detects USB keyboard-wedge magstripe / RFID swipes globally — when a Track 1/Track 2 sentinel (`%` or `;`) arrives via the keydown listener, all subsequent chars are buffered until Enter or `?` and posted to `POST /api/staff/authenticate-card`. Cards are bound to staff via `staff_override_cards` (tenantId, staffId FK cascade, cardNumber unique-per-tenant, label, isActive) and managed in the Staff edit dialog → Override Cards section. Server `extractCardNumber()` strips track sentinels and stores ONLY the PAN digits (never the cardholder name or expiry). Swipe is accepted *everywhere* a `PinPad` mounts (manager overrides, supermarket gate, kiosk unlock, staff login) because detection lives inside `PinPad` itself — no caller changes required. Card endpoint mirrors `/authenticate` (returns staff + permissions, honors `requiredRoles`).
*   **Duplicate Product Finder & Merge**: Detects duplicate products and merges several into one survivor, combining inventory AND re-attributing full transaction history. Detection (`GET /api/products/find-duplicates`, permission via product-management authz) groups active, tenant-scoped products by **exact** normalized name (`normalizeName` lowercases/strips punctuation+whitespace) and by **similar** name via union-find over Levenshtein `similarityRatio ≥ 0.85`; each candidate is flagged `mergeable` (false for variant/composite/composite-child products). Merge (`POST /api/products/merge` `{ survivorId, duplicateIds[] }`) runs in a single `db.transaction`: repoints 12 history tables (order_items, purchase_bill_items, purchases, stock_movements, supplier_return_items, stock_transfers, weight_labels, stock_adjustments, stock_count_items, product_batches, production_batch_items, store_stock_movements) to the survivor, deletes the duplicates' config rows (recipe_ingredients→recipes, pricing_tiers, purchase_units, promotions, product_locations), aggregates `location_inventory` into the survivor via raw `INSERT…SELECT…ON CONFLICT DO UPDATE` (sums quantities), sums the global `stockCount` onto the survivor, then **archives** (soft-delete, `archivedAt`) the duplicates so nothing is hard-deleted. Validates tenant-scope, active-only, dedupe, and rejects variant/composite/composite-child on both sides; writes a `product.merge` audit row. UI lives in `pages/products.tsx`: a "Find Duplicates" toolbar button opens `DuplicateMergeDialog`, which lists `DuplicateGroupCard`s (exact/similar badge); within a card the user picks the survivor and merges. **Gotcha**: do NOT derive the row type via `ReturnType<typeof useFindDuplicateProducts>["data"]` — TS resolves the hook's generic `TData` to `{}`; import the generated `DuplicateGroup` type from `@workspace/api-client-react` instead.
*   **Barcode Scan in Stock Count**: The Stock Count detail view (`StockCountDetail` in `pages/accounting.tsx`) accepts barcode scans (USB keyboard-wedge scanner or manual typing + Enter). Each scan matches the code against `products[].barcode` (normalized trim+lowercase) and adds **+1** to that product's physical count via the existing optimistic `updateCount` PATCH. Rapid scans are made reliable with a synchronous `countsRef` (so the next scan reads the latest value before React re-renders) plus a per-item `writeSeqRef` guard (so a stale PATCH response can't clobber a newer one). Edge cases surface a toast: no match, multiple products sharing a barcode, product not in the session, item already adjusted. The `StockCountDetail` component receives the `products` list (which includes `barcode`) as a prop from `InventoryPanel`.
*   **NEXXUS Mobile App (Expo)**: A single Expo / React Native app (`artifacts/nexus-mobile`, previewPath `/mobile/`, Android minSdk 24 / Android 7+, iOS) covering six POS areas — Sell/Checkout, Catalog, Inventory (stock counts + barcode scan + adjustments), Customers & loyalty, Cash management, Reports/dashboard. It logs in against the existing api-server (`POST /api/saas/login`) and reuses the **same** generated hooks from `@workspace/api-client-react` (wired via `setBaseUrl` + `setAuthTokenGetter` at the top of `app/_layout.tsx`). Endpoints not in the generated client (login, stock-adjustments, stock-counts + apply/items) go through a thin app-local typed fetch helper `lib/nexus-api.ts` that shares the same domain + token. **The shared OpenAPI spec is intentionally left UNTOUCHED** — changing it would regenerate the web client (a major shared change); the mobile-only helper is isolated and lower-risk. Dark navy + blue/cyan branding lives in `constants/colors.ts` (consumed via `hooks/useColors.ts`); JMD currency formatting in `lib/format.ts`. Auth state (`context/AuthContext.tsx`) persists the token + tenant in AsyncStorage and calls `queryClient.clear()` on BOTH sign-in and sign-out to prevent cross-tenant cached data leaking on shared devices. **Stock-count barcode flow** (`app/stock-count/[id].tsx`): expo-camera `CameraView.onBarcodeScanned` maps a scanned code → product → session item and adds +1 to `physicalCount`. Because the server PATCH is an absolute last-write-wins overwrite, rapid scans are made safe with (a) a synchronous `countsRef` holding the latest value, and (b) a **per-item serialized writer** (`flushItem`) that keeps only one PATCH in flight per item and re-sends until the server reflects the latest local value — an out-of-order completion can never regress a count. A 1.2s same-code throttle in the scanner prevents runaway increments from the continuous camera (counting many of one SKU is done via manual edit). Shared/duplicate barcodes are detected (`Map<string, number[]>`) and blocked with a disambiguation prompt instead of silently counting the wrong product. **Responsive / tablet-first**: the app is tablet-primary and switches to a phone layout dynamically by screen width via `hooks/useResponsive.ts` (reads `useWindowDimensions()` so it re-lays-out live on rotate/resize). It exposes `isTablet` (≥768), `isWide` (≥1024), `isLandscape`, `productColumns` (4/3/2), `listColumns` (tablet 2 / phone 1) and `contentMaxWidth` (980/760/undefined). The Sell screen (`app/(tabs)/index.tsx`) renders a **split-view** on tablet (product grid left + a persistent `CheckoutContent` cart panel right) and the floating "View cart" bar + full-screen `Modal` on phone — both reuse the same extracted `CheckoutContent` ({embedded?}) so cart/pricing/checkout logic is shared; a `useEffect` closes the phone-only `checkoutOpen` modal when switching into tablet so rotation can't re-open it. Catalog & Customers use responsive `FlatList numColumns={listColumns}` with a `key` change to force re-layout and `columnWrapperStyle` only when >1. Reports, Cash, Inventory, customer detail and Login center their content with `maxWidth`/`alignSelf:"center"`. **Gotcha**: changing `FlatList numColumns` at runtime REQUIRES a `key` prop change or RN throws. **Checkout parity**: the mobile cart now mirrors desktop — `context/CartContext.tsx` keys lines by a composite `lineKey` (productId + sorted variant/modifier option ids), so the same product with different choices stacks as separate lines; each line carries `variantChoices`, `modifierChoices`, a computed `unitPrice`, and a `lineDiscount` (clamped at write-time AND in the order payload to `[0, unitPrice*qty]`); subtotal = sum(`unitPrice`*qty − `lineDiscount`). `components/CustomizeSheet.tsx` (fed by `useGetProductCustomization`) replaces the old "Use full POS" wall and mirrors desktop price logic exactly — single variant group: `option.priceAdjustment` IS the total price; 2+ groups: match the `combinations` row by label join "/" (falls back to base price on miss, same as desktop); modifiers additive; validates required variant groups + modifier min/max. Composite products with no options add directly. The Sell screen (`app/(tabs)/index.tsx`) also has camera **barcode scan-to-add** via the shared `components/BarcodeScannerModal.tsx` (1.2s same-code debounce, `barcode→productId[]` map so shared barcodes prompt disambiguation instead of guessing); a scanned simple product adds, a variant/modifier product opens the customize sheet. `POST /api/orders` now sends `variantChoices`/`modifierChoices`/`discountAmount` per item. **The shared OpenAPI spec was intentionally left untouched.**
*   **Mobile Direct ESC/POS Receipt Printing**: The Expo app (`artifacts/nexus-mobile`) prints receipts straight to a thermal printer over three transports — **Network** (TCP raw 9100, `react-native-tcp-socket`), **Bluetooth** (BLE, `react-native-ble-plx`, iOS+Android), and **USB** (Android-only, `react-native-thermal-printer`). All printing logic lives in `lib/escpos/`: `builder.ts` ports the desktop receipt layout (`nexus-pos/src/lib/print-receipt.ts`) into plain 32/42-col text (58mm/80mm) + `asciiFold` + `buildReceiptBytes` (ESC@ init + 7-bit body + feed + GS V B partial cut); `transports/{network,bluetooth,usb}.ts` each **lazy-`require()`** their native module inside the function (NEVER a top-level import) so the app still loads in Expo Go and the web preview — a print action only throws a clear "requires a development build" error there. `index.ts` exposes `printReceipt(config, order, settings)`, `testPrint(config)`, and `scanBleDevices()`. Config (enabled/autoPrint/transport/host/port/deviceId/paperWidth) is persisted in AsyncStorage via `context/PrinterContext.tsx` and edited at `app/printer-settings.tsx` (reached via the printer icon in the Sell/Checkout header). On checkout, `app/(tabs)/index.tsx` builds a `ReceiptOrder` from the cart snapshot + order response + `useGetSettings`, auto-prints when `enabled && autoPrint`, and shows a manual "Print receipt" button on the sale-complete screen. **Requires a native development build** — native printing modules do NOT work in Expo Go or the Replit web preview (verification here is limited to typecheck + JS bundle; on-device print is the user's). USB on `react-native-thermal-printer` takes plain TEXT (it emits its own ESC/POS init/cut), so the USB transport sends text while network/BT send raw bytes. **The shared OpenAPI spec was intentionally left untouched** — the receipt types are duplicated locally in `lib/escpos/types.ts`.
*   **Mobile Catalog Management + Subscription Renewal (Expo)**: The Expo app (`artifacts/nexus-mobile`) adds product/customer management and self-serve subscription renewal. **Catalog view toggle** (`app/(tabs)/catalog.tsx`): a card|list segmented toggle persisted in AsyncStorage (`nexus_catalog_view`); list = compact rows, card = grid tiles (columns from `useResponsive` productColumns). Each product card navigates to a **detail screen** (`app/product/[id].tsx`) showing price/cost/stock/taxable plus read-only **volume pricing tiers** and **purchase/sale units**. **Add/Edit product** (`app/product/new.tsx` + `app/product/edit/[id].tsx`, both render the shared `components/ProductForm.tsx`): core fields via `useCreateProduct`/`useUpdateProduct`, then the tiers + units are saved via a **second PUT** through the app-local helpers (`replacePricingTiers`/`replacePurchaseUnits` in `lib/nexus-api.ts`) — the shared OpenAPI spec stays untouched. The tier/unit editors live in `components/PricingUnitsEditor.tsx` (string-backed drafts for smooth text input; client-side validation mirrors the server: tier maxQty≥minQty, unit conversion>0, must be purchase OR sale, no dup names). **Add customer**: a "+" header button on `app/(tabs)/customers.tsx` opens a modal form (`useCreateCustomer`, refetch on success). **Subscription renewal** (`app/subscription.tsx`, reached via the person icon in the Sell header): shows plan/status/renewal from `GET /api/saas/me` and opens a **secure in-app web checkout** via `expo-web-browser` `openBrowserAsync` to the web `/subscription?token=…` page, reusing the existing web PayPal/PowerTranz 3DS flow. The web entry (`artifacts/nexus-pos/src/main.tsx`) reads `?token=` from the URL, writes it to localStorage before render (so `ProtectedRoute` authenticates), then strips the param via `history.replaceState`. `AuthContext` persists the `subscription` returned by login in AsyncStorage. **Gotcha**: do NOT type product rows via `ReturnType<typeof useListProducts>["data"][number]` (resolves to `{}`) — import the generated `Product` type.
*   **Supermarket POS Layout (scan-only)**: An alternative POS layout (`pages/pos-supermarket.tsx`) built for high-speed checkout lanes. Gated by a global tenant setting `supermarket_ui_mode` (Settings → POS Interface) that is **mutually exclusive** with `hardware_ui_mode` — turning one toggle on turns the other off, and the `PosModeDispatcher` in `App.tsx` checks supermarket FIRST (precedence), then hardware, then standard. Items are added **only by SKU/barcode** (the main `products` table has no `sku` field — matching is on `barcode`, normalized; 0 matches / duplicate barcode / variant-or-modifier products surface a toast and are not added — variant/modifier items must use the standard POS). Layout: a big/bold bill preview fills the LEFT (large per-line totals, inline +/- and remove, a huge TOTAL + Change Due); the RIGHT column holds an always-focused scan box (Enter-to-add), a numeric quantity keypad (sets qty for the next scan, or "Set Quantity" on a selected line), optional customer, cash/card toggle with cash-tendered/change-due, and a large checkout button. The scan input is kept focused via a `focusScanInput()` rAF helper called after keypad/cart interactions and on every dialog close so USB scanners keep working. Reuses the same hooks (`useListProducts`/`useCreateOrder`/`useGetSettings`/`useGetCurrentCashSession`/`useListCustomers`/`useCreateCustomer`) and the same receipt pipeline (`receiptOrderFrom`/`buildReceiptHtml`/`printOrderReceipt`) as the other layouts. All existing guards apply: PIN lock, open-shift/cash-session gate, and the supermarket-mode manager-PIN gate (decrease/remove/clear/qty-reduction when a cashier is logged in). **Frontend-only** — no API/DB/OpenAPI changes (the `createOrder` body is cast `as any` for `cashTendered`, the established pattern). **Out of scope (deviation)**: discount and hold/recall were intentionally omitted to keep the lane UI focused.
*   **Kiosk Lockdown**: App-wide (`KioskLock` in `App.tsx`). Entering fullscreen arms the kiosk; any subsequent exit from fullscreen (ESC, F11, browser menu, page reload) opens a blocking PIN overlay that only a manager/admin/supervisor can dismiss. The armed flag is persisted in `sessionStorage` (`nexxus_kiosk_armed`) so reload cannot bypass it. While armed, a `beforeunload` handler also triggers the browser's native "Leave site?" prompt on any tab close, reload, or navigation attempt — the strongest guard the web platform permits without browser-level kiosk mode. The lock offers a "Re-enter Fullscreen" escape that does not require PIN.

## Gotchas

*   **Web receipt printing (browser print; Android prints a lean plain-text receipt)**: The web POS prints **every** receipt through the browser's native print pipeline. `src/lib/print-receipt.ts` is a thin wrapper — `printOrderReceipt(html, order, settings)` (synchronous, `void`) calls `openReceiptWindow(html)` in `src/lib/receipt.ts` (hidden same-origin iframe + `window.print()`, handles pop-up blockers, KioskLock coordination, and `@media print`). This works on any installed printer (thermal/inkjet/laser), supports "Save as PDF", and lets the cashier pick the printer. **Android exception**: on Android (`/Android/i` UA test in `print-receipt.ts`), `printOrderReceipt` ignores the passed-in styled `html` and instead prints `buildPlainReceiptHtml(order, settings)` — a stripped-down, **image-free** receipt (NO logo, NO giant pickup number, no colors, compact monospace text sized to `receipt_size`). **Why**: Android stores route browser print through ESC/POS pass-through print services (e.g. Looped Labs "ESC POS USB Print Service") that **crash** ("…keeps stopping"/"…has stopped") when the rendered bitmap is large; the lean page renders to a small bitmap they print reliably. **TWO levers, both required**: (1) lean content, and (2) **page format** — the printed page MUST be pinned to the exact thermal width via `@page { size: <w> auto; margin: 0 }` + explicit `html,body { width: <w> }`. Lever (2) turned out to be the bigger one: stripping content alone did NOT stop the crash (a user confirmed via the Android print *preview* that the lean text was already rendering yet still crashed) — without the zero-margin + pinned-width, the browser hands the service a Letter/A4-sized mostly-blank canvas that rasterizes huge and crashes it. **Critical architectural gotcha — Android must call `window.print()` on the parent**: `openReceiptWindow` uses a hidden iframe. On Android Chrome, calling `iframe.contentWindow.print()` can silently ignore `@page` rules and produce a full Letter/A4 PDF regardless of CSS. The correct Android path: (1) inject `@page { size: <w> auto; margin: 0 }` into the **parent document** (`<style id="nexus-print-page">`, cleaned up on `afterprint`); (2) give the iframe a real off-screen width (`left:-9999px; width:80mm`) so content lays out correctly; (3) call **`window.print()`** on the **top-level parent window** (NOT `cw.print()`); (4) do NOT inject a self-print `<script>` into the Android iframe. `openReceiptWindow(html, opts?)` — Android passes `opts.receiptPageSize`; desktop passes nothing and keeps the old iframe path unchanged. **Desktop/Windows is deliberately left unchanged** — it still prints the full styled `buildReceiptHtml` output. **History**: a previous WebUSB raw-ESC/POS path (`escpos-usb.ts` + per-device `usb-printer-settings.tsx`) and an even older Looped Labs **Android intent** path (`escpos_print_enabled`/`escpos_connection` settings) were both removed entirely. (Mobile Expo direct ESC/POS thermal printing is a separate, unrelated feature and is unaffected.)

*   **Multi-unit product quantity edits**: Direct quantity edits for multi-unit products snap to the nearest whole multiple of the unit factor on commit.
*   **Technician Impersonation**: Technician-impersonated sessions carry `restrictedRole: "technician"` in the JWT. Server-side: `requireFullTenant()` in orders, cash, topup, purchases, held-orders rejects writes. Frontend: nav filtered via `isTechnicianRestricted()` in `lib/tenant-token.ts`; `TECHNICIAN_ALLOWED_PATHS` lists permitted routes.
*   **Database Migrations**: Always run `pnpm --filter @workspace/db run push` from the workspace root after schema changes.
*   **Supermarket Mode gate location**: PIN gate logic lives in `pos.tsx` (`needsSupermarketAuth`, `requestSupermarketAction`, `executeSupermarketAction`). To extend coverage to a new cart action, route its onClick through `requestSupermarketAction({ type: "...", ... })` and handle the new variant in `executeSupermarketAction`.
*   **Purchase Bill totals are authoritative on the server**: never trust the client for `subtotal`/`taxTotal`/`totalCost` — the POST handler in `purchase-bills.ts` recomputes them from items, and `confirmBillSideEffects` will repair zeroed totals on legacy drafts before posting the JE. To add a new cart action that posts to accounting, follow the same transaction pattern (`db.transaction(async (tx) => …)`) so a mid-flight failure cannot leave stock half-applied.
*   **PinPad auto-submit threshold**: `PinPad` only auto-submits when `digits.length === pinLength` (the *max*). Setting `pinLength={4}` on a caller makes 4-digit PINs auto-submit but blocks anyone with a 5–8 digit PIN. The defaults (max 8, min 4) are correct for nearly all call sites; only override if the dialog truly only accepts a fixed length.
*   **Drizzle push interactive prompt**: `pnpm --filter @workspace/db run push` is currently blocked by an unrelated `tenants_slug_unique` constraint prompt. For additive column changes, apply the SQL directly (via `executeSql` in the code execution sandbox) rather than waiting on the migration tool.
